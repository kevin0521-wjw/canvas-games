# `_tools/` 与 `_reports/` —— 平衡性探针与诊断脚本

这两目录不是游戏，也不是判据。它们是**「调数值之前先量」**留下的工具与证据，
留档的理由很简单：探针里的注释记的是**当时错在哪**（探针自己犯了什么错、
哪条结论差点被当成游戏 bug），比脚本本身更值钱。

## 目录用途

| 目录 | 内容 | 什么时候需要 |
|---|---|---|
| `_tools/` | 探针与一次性修复脚本（Node + 手写 CDP WebSocket，零依赖） | 要改数值前先重跑 |
| `_reports/` | 最近一次运行这些工具的原始输出 | 核对「某条结论是怎么来的」 |

## 工具清单

| 脚本 | 回答什么问题 | 怎么跑 |
|---|---|---|
| `balance-probe3.cjs` | 四段式基线：① 六张符卡能不能在限时内打掉 ② 三关难度是爬坡还是断崖 ③ 不作弊的 AI 能推到哪 ④ 成长引擎转不转得动 | `node _tools/balance-probe3.cjs`（在 `games/` 下） |
| `ai-many.cjs` | AI 存活/推进的**多轮分布**。单轮方差能差 3 倍，判定必须看多轮 | `node _tools/ai-many.cjs 14` |
| `ai-diag.cjs` | **归因**：AI 每次失机时抓现场快照（关卡、在场弹、正在打的符卡与剩余血）。用来判断「是打不过」还是「一直在躲」 | `node _tools/ai-diag.cjs` |
| `statediag.cjs` | 状态机逐帧采样。查「进不去 Boss 战 / 状态切不过去」这类问题 | `node _tools/statediag.cjs` |
| `ddiag.cjs` | 最小诊断：造一个敌人 + 打一发，看命中/伤害路径到底走没走通 | `node _tools/ddiag.cjs` |
| `patch-readywait2.cjs` | 批量把判据里的「固定 sleep 等页面加载完」换成轮询就绪条件（幂等，可重复跑） | `node _tools/patch-readywait2.cjs` |
| `patch-readme.cjs` | README 状态行与新增章节的补丁（幂等） | `node _tools/patch-readme.cjs` |
| `probe-selfcheck.cjs` | 探针收尾的**幂等规范化 + 四重自检**（括号 / 语法 / 路径 / 收尾函数是否都有定义）。改完探针先跑它 | `node _tools/probe-selfcheck.cjs [--check]` |
| `_cleanup-helper.js` | 收尾辅助函数的**唯一原文**（被 `probe-selfcheck.cjs` 插入到各探针里） | 不直接跑 |
| `_rmprofile.js` | 异步删 profile 的接力脚本（由 `dropProfile()` 自动 spawn） | 不直接跑 |

所有脚本路径都按 `_tools/` 为基准解析（`path.resolve(__dirname, '../…')`），
在 `games/` 下用 `node _tools/<名字>` 跑即可。

## ★★ 收尾为什么这么绕（三次返工才做对）

这些探针每次跑都会在 `_tools/` 下留一个**几百文件的 headless profile**。
修它花的时间比写探针本身还长，而每一步都踩了新坑：

| 尝试 | 做法 | 结果 |
|---|---|---|
| ① | `execFileSync('cmd rmdir')` 同步删 | 235 个文件时 **15 秒仍超时** |
| ② | 同步删 + 重试两次 | 更慢，而且退出前根本没时间重试 |
| ③ | 换成逐文件删 | 同样是飘的（一次 169,680ms、另一次 14ms/文件） |
| ④ | detached 子进程异步删 | 仍失败 —— 但**真因不在删除**（见下） |
| ⑤ | 补上缺失的 `sleepSync` | ✅ 跑完即触发删除，12 秒内清干净 |

**真因是一个更隐蔽的问题**：收尾第一行写的是 `killTree(proc.pid); sleepSync(700);`，
而 `sleepSync` 在某次重构里没被一起插入 → **那一行抛 `ReferenceError`，
后面的 `dropProfile(profile)` 全是死代码**。而结论（`out(...)`）在收尾之前就打完了，
所以**日志看起来一切正常**，只是 profile 一次都没被删掉过。

由此加了两条规矩：

1. **`execFileSync` 只报 `ETIMEDOUT`，看不到真实原因** —— 想知道「是被超时杀的还是自己失败」，
   得用 `spawnSync` 并打印 `status` / `signal` / `stderr`。我一度以为是「Edge 没退干净」，
   去查进程发现 Edge 早就退了；而 `spawnSync` 一眼就看出 `signal=SIGTERM、stderr 全空`。
   （中途还绕了一圈去删那些残留 Edge —— 那一堆其实是被中断的探针留下的，不是当前这个的。）
2. **「语法通过」≠「收尾真的会跑」**。所以 `probe-selfcheck.cjs` 除了括号/语法/路径，
   还要查「收尾段里调到的每个自定义函数是否都有定义」——
   否则拼错一个名字就是整段清理变成死代码，而外部完全看不出来。

另外：**改批量脚本时，「插入点锚定」和「内容替换」必须分开做**。
第一版用 `replace` 处理收尾调用、又用 `indexOf` 插入辅助函数，两个操作叠加
把 `function connect(` 的函数体开头吃掉了（`node --check` 报 `Unexpected token '}'`）。
还有：**每条替换都要有幂等守卫** —— 没守卫时连跑两次就出现 4 条冲刷语句，
括号数从 137 涨到 139，脚本自己在造垃圾。现在 `probe-selfcheck.cjs` 连跑三次都是「无改动」。

## ★ 使用前必读：探针会自己犯错

这三个工具报出来的「结论」**不能直接拿去改游戏数值**。三次真实误报：

| 探针报的现象 | 真实原因 |
|---|---|
| 六张符卡全部「没能进到第 N 张」 | 那次是**真 bug**，但只在测试路径上：`spawnBoss()` 全代码只有 `updateWaves` 里一个调用点，而 `updateWaves` 被 `if (!boss && !run.noSpawn)` 挡住 → 一设 `noSpawn`，Boss 永不出现 |
| 三关敌舰数全是 0 | 探针**自己**设了 `noSpawn = true`（那正是关掉刷怪的开关） |
| 补给舱掉率 0%（600 次击杀） | `mkShot(x,y,off,dmg,spd,…)` 写成了 `(x,y,0,8,999,0)` —— **把速度当伤害传**，弹速 999px/帧一帧飞出场地被出界判定吃掉，敌人一枪没中，而分母却按 600 算 |

两条硬规矩：

1. **任何比率型指标，分母必须是被验证过的事件数，不是循环次数。**
2. **探针报出的每个数字，先回答「谁定义的」** —— 这个数是探针造的，还是游戏本来就有的。

## ★ A 段的坑：探针必须会瞄准

`balance-probe3` 的 A 段每帧执行 `player.y = boss.y`。
第一版探针没做这件事，让玩家钉在 y=240，而 Boss 的 y 在 ±170 间摆动 ——
于是「每张符卡都打满时限」看起来像游戏缺陷，实际是**探针没瞄准**。
差点照着假数据去改 Boss 血量。

## ★ 改数值之前先归因，别直接改

2026-10-13 那轮的教训：`ai-diag` 报出 AI 在第 2 关两次死亡，
两次死亡瞬间**那张符卡的剩余血是 206/225 和 199/225** —— 几乎没掉血。

这说明它不是「打不过」，是**一直在躲、从来不瞄准**：
躲避项系数 `5.2 × w²` 在 134 发弹下饱和，把瞄准权重（最大 ±3.5）整个盖过。

而 `balance-probe3` 的 A 段已经证明那张卡**数值上可达**（仅 Z 61% 限时、双开 38% 限时打掉）。
所以该改 AI，不是改 Boss 血量 —— **顺序反了就把 AI 的锅甩给了游戏数值**。

## 报告怎么看

- `_reports/balance-probe3.log` —— 四段式基线。改完数值应该重新跑一遍做对比。
- `_reports/aimany.log` —— AI 多轮分布（存活秒/最远关/失机/击破/开箱 + 中位数汇总）。
- `_reports/statediag.log` / `ddiag.log` —— 两次「问题看似在游戏、其实在测试侧」的现场记录。

原始数据在同名 `.json` 里（便于跨轮次做差分对比）。
