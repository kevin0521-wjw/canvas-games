一、本轮（v1.5.0 → v1.5.1）改了什么

起点是一条用户实测反馈：「元素阵：射速过快，墙移动太慢 + 血量太低；应该有随机的环境内触发风/水/火/雷弹幕；加一个冰弹，同样遵循元素反应」。拆成四件事，外加一个录制演示时暴露出来的真 bug。

① 三项数值反向调整

项旧值的问题新值实测
射速 命中返还 8 帧 → 净冷却只剩 18 帧（0.3s），按住不放等于连发 fireCd 26→40、命中返还 8→5 净冷却 35 帧（0.58s），「瞄着打」与「乱按」正式拉开差距
墙速 8.8+0.36n px/s，走完 544px 要 62 秒，比清完一面墙还慢，墙成了背景板 21+0.55n px/s；减速余量同比放大 3.2→9.5 10 秒实测下移 214.6px（配置预期 ≈215），减速上限约为墙速 45%、仍留 35% 速度下限
符块血量 9+1.5n，而直接伤害是 12，无反应也一发一块，护甲与元素反应一起失效 14+2.2n 直接命中最少剩 2 血，≥1.3 倍反应才能一发破
为什么是「反向」：v1.4.0 并档时按全站统一的「降难度」口径，把元素阵的心 4→5、墙速 10.5+0.55n→8.8+0.36n、符块血 10+2n→9+1.5n 一并压了下来。但元素阵的难度模型和另外五款不同。它的压力不来自敌人数量，而来自「元素反应是否构成硬约束」。压到血 9 之后，那条约束就断了：直接伤害 12 能一发一块，谁还 care 用什么元素。同一套「缓曲线」手法，用在那五款上是对的，用在这款上是把截距压到了机制阈值以下。

② 天象：会触发反应的环境弹幕

普通阵每 3~5 秒随机落一发带元素的弹幕，落前 0.75 秒在顶部画一条虚线预警 + 元素名 + 三角标。

元素弹道性格逼玩家做什么
火直线快（4.6）压迫感，正面让开
水慢（2.6）但半径 8，命中溅成两滴封走位。水滴是抛物线（轻重力 0.045），不能按直线躲
雷Z 字横摆（vx = sin(age*0.22)*2.2）不好预判，得提前离场
风从屏幕侧面斜进来（左右随机）逼你离开舒适位
冰中速（3.6），命中玩家冻 1.5 秒移速 ×0.55 的那 1.5 秒里躲不开别的东西

双刃设计：天象弹打在符块上会触发完整元素反应（走同一个 hitBlock），但 fromEnv = true 时不计分、不给墙减速。于是「躲」是保命，「故意接在符块上」是白拿一次反应。但不给分，站着刷天象没有收益。Boss 阵自动熄火（spawnBoss 把 timer 设成 1e9）：Boss 自己就在发弹幕，再叠天象就是地狱。

③ 冰：第五个元素，三条反应

cryo（5 键直选、Q 循环覆盖五个），颜色压到青、符纹用雪花以区别于深蓝的水滴。

反应组合与倍率效果设计意图
融化冰×火 2.0 / 火×冰 1.6最高单体倍率，但熄火、并把邻块打湿 90 帧冰系版蒸发：强，但消耗状态
冻结冰×水 1.0 / 水×冰 1.2 / 冰×冰块临时 +5 护甲（150 帧）变硬；火/雷打上去破冰 1.8 倍 + 邻居 0.3 溅射本身没有收益，是给下一发铺路的状态
超导冰×雷 1.4 / 雷×冰 1.3108px 内削 3 点护甲，并对范围内其他块造成半伤溅射范围削甲，让直接伤害重新打得动

冰×冰也走冻结（reactionOf 里的显式例外，没进 RX 表）。语义上「自己冻自己」比「自己烧自己」通，而且给了一条不带水也能挂冻结的路径（环境水弹同样能挂）。风×冰照旧走扩散。

这制造了一个二段循环：先挂冻结让块变硬，再上火/雷破冰拿 1.8 倍并溅射到邻居。判据用精确值钉住它：破冰一轮 10 × 1.6 × 1.8 = 28.8、冰甲未破 10 × 1.1 × 0.6 = 6.6，差 4.4 倍，手感上是「打对了」和「打错了」的分界。

④ 录制演示时挖出来的真 bug：AI 永远不会选冰

补录元素阵演示时，发现 AI 接管下冰一次都没被选中过。原因在 AI 的选元素逻辑：

// 旧：取「第一个倍率 ≥1.3 的元素」
good = EL_ORDER.find(e => {
  const r = reactionOf(e, def);
  return r && r.mul >= 1.3 && r.kind !== 'burn';
}) || 'anemo';

这是顺序不是强弱。冰的三条反应单发倍率都不占优（融化 2.0 与蒸发 2.0 打平、冻结 1.0、超导 1.4 低于超载 1.5），而 EL_ORDER 里火水雷风排在冰前面，find 永远轮不到冰。冰在 AI 模式下是死内容：玩家手动按 5 能用，AI 永远不会用。

修法是给冰单独记一个「组合价值」，因为它的收益要两发才兑现：

const oneShot = e => { const r = reactionOf(e, def);
  return (r && r.kind !== 'burn') ? r.mul : 0; };
const combo = e => {
  if (e !== 'cryo') return 0;
  if (def === 'hydro' || def === 'cryo') return 1.8;  // 冻住一片 → 破冰 1.8 倍 + 溅射
  if (def === 'electro') return 1.5;                   // 超导：范围削甲 + 半伤溅射
  return 0;
};
let bestScore = 0; good = 'anemo';
for (const e of EL_ORDER) {
  const s = Math.max(oneShot(e), combo(e));
  if (s > bestScore) { bestScore = s; good = e; }
}

改完之后 AI 会自动打出「冰 → 冻结 → 火破冰 1.8 倍 + 溅射」这条二段循环，也就是 v1.5.0 最想让人玩到的那个动作。补了一条判据钉住它（水块上选冰、冻住后改用火）。

这条 bug 的性质值得记一笔：它不是「AI 打不赢」，而是新加的元素在 AI 眼里不存在。判据全绿（31 项）也照样绿，因为没有一条断言检查「AI 会不会用新元素」。加新机制时，要同时问一句「AI 能不能用上它」。

二、这一轮踩过的坑

  1. NaN 陷阱：b.frozen <= 0。当 frozen 字段不存在（undefined）时，这个比较恒为 false，于是燃烧 DoT 会静默停摆，而且不报错。安全写法是 !(b.frozen > 0)。
  2. 判据必须命中当帧抓：水弹分裂出的小水滴带横漂和轻重力，飞一会儿就被回收或出界。step(120) 之后数只能看到「剩下的」，会误报「0 滴」。
  3. 分裂弹不能原地生成。出生点上移 5px、给 vy = -1.2 斜上溅出，否则下一帧就被同一块符块继续吃掉。
  4. 加第五元素时 % 4 全部要改成 % EL_ORDER.length：Boss 元素轮转、符阵排布、AI 选元素三处都写死了 4，加冰后会漏轮转。
  5. freeze() 会停掉 rAF。冻结后连续截图得到的是完全相同的字节。视觉验证必须让 rAF 自己画。

五、怎么玩、怎么跑

玩

每款游戏就是一个 index.html，双击即玩，不需要服务器、不联网、没有第三方库。 个别浏览器对本地 file:// 媒体有限制，那就起个静态服务器：

cd games
npx serve .
# 然后打开 http://localhost:3000/

快捷键（六款基本统一）

移动开火其它
通用← → ↑ ↓ / WASD空格暂停 P · AI 接管 E · 二倍速 T
符箓灵弹 · 元素阵← → 走位　↑ ↓ 瞄准空格（带元素）1–5 / Q 换元素（火水雷风冰）· P 暂停

跑判据

需要 Node.js 18+ 与本机的 Edge 或 Chrome。

cd games
node _run_all.js                # 六款全跑，约 40 秒
node talisman-array/verify/smoke.js index.html __TP   # 单款

判据跑在真实浏览器里（headless Edge + 原生 WebSocket 直连 CDP，不引 puppeteer），不是 jsdom 模拟。因为要验的东西有一半是「画出来对不对」。结果落到 _logs/，档案页上的断言数是从日志自动回填的，不是手填。

录演示

node _tools/record-demo.cjs --game talisman-array --out "06_符箓灵弹-元素阵.mp4"

冻结 rAF 后按固定步长推进、逐帧抓画布像素、交给 ffmpeg 压 H.264 。所以同一份代码每次录出来的画面完全一致，返工只要重跑脚本。

七、文档这一轮也重做了一遍

按用户要求把 开发过程与借鉴分析.pdf 整篇重写：叙事重心从「技术拆解」换成 「心路历程」。从太空射击（Space Invaders 1978 → Galaga → R-Type → Batsugun 1993 判定点缩小 = 弹幕诞生 → 东方）与肉鸽（Rogue 1980 → 1993 年连流派名都是 Usenet 社区投票出来的 → 2008 柏林解释 → Spelunky / 以撒 / FTL → Hades 2020 把死亡写进叙事）两条设计血脉讲起， 再顺着讲每一款游戏背后的选择、撞过的墙、以及判断标准的演变。 24 页 → 25 页，技术内容一个没删，挪进了附录 A。

顺手修掉一个「从头到尾零报错」的静默失败 新写的源 HTML 里，1.2.4 那张时间线的 5 行各少写一个 </div>。 HTML 解析器会自动补齐。页面能显示、没有任何报错，但后面所有内容都被塞进 第一行的 .txt（一个 flex 子项，min-content 只有 47px）→ 表格全被压成 260px 的竖条、文档撑到上百页 → Chrome 的 print-to-PDF 只吐了 9 页就停，正文只剩三分之一。

误导人的地方在于：消融实验（改分页 CSS、开/关背景打印）显示产物都精确停在同一字节数， 看起来像「Chrome 有个 2.26MB 硬上限」，那是假结论，最后还是靠数标签开合次数定位到真凶。

两道护栏就此加上，且都做了回归验证（把 bug 复原回去，护栏精确报出「div（120 开 / 115 闭）」并拒绝出片）：

  1. _syntaxcheck.js 增加 docs/*.html 的标签配平检查（<div> / <table> / <tr> / <td> / <ul> / <li> / <p> / <pre> 开合必须相等），进标准回归；
  2. _tools/build-pdf.cjs 出片前读源文件做同样的检查（不能读 DOM：解析器已补齐，DOM 永远配平），出片后比对「实际页数 vs 布局估算页数」，低于 60% 即判为被截断并报错退出。
这一条其实是第五章的延续 「判据全绿不等于对」说的是游戏逻辑；这一条说的是文档本身： 一份 25 页的 PDF 少印了 16 页，而生成它的那条命令返回了成功。

任何「跑完就当成了」的流程，都需要一条「跑完了但结果对不对」的检查。 这正是本仓库从第一天就在做的事，只不过这次主角从游戏换成了文档。

文档里的史实都有出处

设计笔记第一、二章提到的每个年份、开发者和机制，都在附录 D「参考资料与延伸观看」里配了出处： D.1 太空射击 22 条、D.2 肉鸽 9 条，逐条标了「作品 / 年份 / 文中位置 / 出处」； D.3 收 10 条视频与讲座；D.4 收 6 条延伸阅读与查证工具。

链接是实测的，而且踩了一个坑 所有 URL 在 2026-11-10 逐条发 HTTP 请求确认可达，只收 200 的。 踩到的坑值得记：GDC Vault 的地址形如 play/<ID>/任意标题，后半截标题随便写都返回 200， 真正内容只看 ID —— 我按「地址能打开」筛出的两条，打开确实是 200，标题却是别的演讲。 所以每个 GDC 链接都改成按页面标题逐条核对，宁可少收也不放假出处。

另外，Chrome 的 print-to-pdf 会保留外链标注，所以这份 PDF 印出来链接是可点的： 30 页里有 58 条可点击标注、覆盖 47 个不同 URL。

八、素材与版权

六款游戏的图形全部由 Canvas 2D API 程序化绘制：没有位图素材、没有外部字体、没有音频文件、没有第三方库。借鉴的是玩法机制与视觉语言（原神元素反应、东方弹幕、元气骑士房间循环、打砖块反弹角、雷电三阶段），未使用任何第三方模型、贴图或字体资源。
