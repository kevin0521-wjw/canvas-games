2 · 共同骨架与三种代码风格

五款的玩法差别很大，但工程骨架是同一套。把它们拆开对齐后，能看出一个很稳定的八层结构。

层职责五款的实现方式
① 舞台固定逻辑分辨率 + fit() 等比缩放写死 W/H，CSS 只改显示尺寸，坐标永不换算
② 配置数值集中，改手感只改一处初版是 CFG 二十一组；其余是顶部常量区
③ 状态一局的所有可变数据统一 newRun() 返回一个大对象，重开即重建
④ 输入键盘 / 指针 / 触屏 → 一个方向量玩家输入对象 K 与 AI 输入 AIK 在 inp() 合并
⑤ 时钟rAF → 归一化 dt → 固定步长全部 dt / 16.6667，再 clamp(dt, 0, 3)
⑥ 更新按固定次序推进子系统update(1) 只接收 1，绝不接收缩放后的 dt
⑦ 渲染背景 → 实体 → 粒子 → HUD → 屏幕级反馈层序固定；反馈画在屏幕坐标系，不进世界坐标
⑧ 探针把内部状态暴露给无头测试window.__SL / __TP / __DM / __SK / __SpaceLine

三种代码风格（同一套骨架的不同表达）

A · 配置驱动 + class（初版）
13 个实体类，各自 update(dt, input) / draw(ctx)，Game 是单例对象字面量。全部数值进 CFG。可读性最好，文件也最长（5,619 行）。
B · 纯函数 + 模块级变量（符箓 / 星屑 / 深渊 / 星轨）
实体就是普通对象字面量，数组 bullets / enemies / parts 挂在模块作用域。没有 class、没有 this，靠命名前缀区分系统。
C · 加密作用域（符箓 / 初版）
(function(){ … })() 包起来，内部 const 不泄漏。外层只能拿到显式挂的 window.__XX。星屑/深渊/星轨没包，靠顶层的 const 落在脚本作用域里。

为什么统一「dt 归一化成帧数」

五款的 update 收的都是「多少帧」而不是秒。全项目只有一处除以 16.6667，其余代码里 dt * 3 就是「3 帧走这么远」。好处是数值可以直接按 60fps 手写（球速 9 像素/帧），坏处是所有以秒计的计时器必须乘 0.0166 —— 符箓灵弹的无敌帧就是因为漏了这个系数，从 1.15 秒缩成 1 帧，玩家会被同一波连扣三下。

3 · 星际防线 · 初版

五款里唯一的重工程写法：13 个实体类 + 21 组配置 + 一套 205 格的网格搜索 AI。文件头自带了 70 行中文结构说明。

3.1 配置驱动：手感被拆成可改的标量

WEAPON: {
  PULSE: { key:'pulse', name:'单发', cd:0.13, dmg:1 },
  TWIN:  { key:'twin',  name:'双列', cd:0.17, dmg:1, offset:11 },
  LASER: { key:'laser', name:'激光', cd:0,    dps:16, width:10 }
},

三把枪是同一张表的三行；新增武器只需加一行 + 一个分支。触摸手感同样被压成三个标量（FOLLOW=17 跟手程度、DRAG_GAIN=1.42 手指 1px 等于飞船几 px、TAP_MS=220）。其中 1.42 是纯算术补偿：手机可用宽约 360 CSS px，逻辑宽 800，1:1 时飞船物理上够不到两侧。

3.2 难度：连续时间 → 阶梯等级

this.elapsed += dt;
const lv = 1 + Math.floor(this.elapsed / CFG.DIFFICULTY.SECONDS_PER_LEVEL);
const newLevel = Math.min(CFG.DIFFICULTY.MAX_LEVEL, lv);   // 16 秒一级，上限 12

等级是阶梯，但三个消费量都是等级的线性函数，所以同级内手感恒定、跨级瞬间跳变：

量公式Lv.1Lv.5Lv.12
敌机速度95 + 14·(lv-1)，再乘随机 0.82~1.1895151249 px/s
生成基础间隔max(0.32, 1.05 − 0.06·(lv-1))1.05 s0.81 s0.39 s
精英概率min(0.42, 0.06 + 0.05·(lv-1))6%26%42%（Lv.8 封顶）
两个从代码里读出来、注释没写的副作用：① MIN_INTERVAL 只约束基础值，最后还要乘 0.55~1.45 的随机，所以 Lv.12 实际区间是 0.21~0.57 秒，下限会击穿 0.32；② MAX_LEVEL=12 与 BOSS.EVERY_LEVELS=5 组合后，一局最多只会出现 2 个 BOSS（第 3 个需要 Lv.15）。

3.3 主循环：两次钳制

let dt = (ts - this._lastTs) / 1000;
if (!isFinite(dt) || dt < 0) dt = 0;      // 时钟回拨 / NaN 归零
dt = Math.min(dt, CFG.MAX_DT);            // 1/30 秒
…
let step = dt;
if (this.state === 'playing' && this.timeScale !== 1) {
  step = Math.min(dt * this.timeScale, CFG.MAX_DT);   // 缩放后再钳一次
}

第二处钳制是关键：二倍速在 60Hz 下 16.7ms × 2 = 33.3ms，正好等于 MAX_DT；若不再钳，最大逻辑步长会变成 1/15 秒，640px/s 的子单帧走 42.7px，可能跨过 48px 的重叠带。代价是帧率低于 30 时二倍速自动衰减回一倍速 —— 代码选择了「宁可慢，不漏判」。

配套还有两条时间轴：elapsed（吃倍速，驱动难度）与 realElapsed（不吃，用于结算），否则二倍速下的「存活 60 秒」就是假话。

3.4 碰撞：没有空间分区

for (let j = this.bullets.length - 1; j >= 0; j--) {
  const b = this.bullets[j];
  if (!aabbOverlap(b.box, eb)) continue;
  const dmg = b.damage;
  this.bullets.splice(j, 1);          // 命中即消耗
  if (e.hit(dmg)) { this.enemies.splice(i, 1); this.killEnemy(e); break; }
}

子弹 × 敌人是全量两两 O(E×B)，没有网格或四叉树。选 AABB 的理由：子弹与敌人都近似方正，4 次比较，是每帧跑几百次的热点；而玩家相关全用圆（circleOverlap 比距离平方，省一次 sqrt，且擦弹更符合直觉）。

实体上限：粒子有 700 的软上限（判断写在 if (len > MAX) return，一次 60 粒爆可以顶到 760）；子弹/敌人/敌弹无硬上限，靠出界回收与生成间隔自然约束。

3.5 打击反馈：从世界坐标搬到屏幕坐标

impactWeights() {
  if (!(this.impactT > 0)) return { l:0, r:0, t:0, b:0 };
  if (this.impactOmni) return { l:.7, r:.7, t:.7, b:.7 };
  const c = Math.cos(this.impactAng), s = Math.sin(this.impactAng);
  return { l: Math.max(0,-c)+0.12, r: Math.max(0,c)+0.12,
           t: Math.max(0,-s)+0.12, b: Math.max(0,s)+0.12 };
}

旧的震屏被删除而不是调小，因为抖动会让弹幕真实位置短暂失真 —— 对靠读弹幕活命的游戏这是功能性伤害。替代方案只写 4 个标量（强度/角度/全向/颜色），用 cos/sin 分解成四条边的权重，各留 0.12 底数。这个方法被特意抽成独立函数，因为判据要断言「左侧受击时左边缘更亮」，渲染与测试必须读同一份真相。

4 · 符箓灵弹 · 巧阵

弹球 + 元素反应 + 一面缓缓下压的符阵墙。这是五款里机制最新的一款，也最依赖「几何解算」而不是「遍历检测」。

4.1 核心威胁模型：不是弹幕，是空间被吃掉

const rows = boss ? 3 : Math.min(2 + Math.floor((n - 1) / 2), 5);
run.wallY = 82;                 // 从可见区顶部淡入，不是从屏幕外飘进来
run.wallFade = 0;
run.wallSpeed = 10.5 + n * 0.55;
const baseHp = 10 + n * 2;

第 1 阵 2 排共 16 块，此后每两阵加一排（最多 5 排），血量线性增长。墙从 y=82 开始，越过 DANGER_Y=816 判突破：同排一起碎 + 扣一颗心。所以玩家的核心压力是「清得比它压得快」，而不是「躲子弹」。

取「最下面」那一排（b.row 最大）而不是数组里第一个越线的 —— 数组按 row 升序生成，第一个越线的反而是最上面那排。取错就表现为「底下几排一起压下来，却只扣上面那排」。

4.2 四元素反应：在伤害结算的最前面插一张表

const RX = {
  'hydro+pyro':    { name:'蒸发', mul:2.0, kind:'vapor', rgb:'255,138,74' },
  'pyro+hydro':    { name:'蒸发', mul:1.6, kind:'vapor', rgb:'255,138,74' },
  'pyro+electro':  { name:'超载', mul:1.5, kind:'aoe',   rgb:'176,110,240' },
  'electro+hydro': { name:'感电', mul:1.3, kind:'chain', rgb:'132,116,240' },
};

方向是有区别的：水打火 ×2.0、火打水 ×1.6。风不与任何元素成对，而是单独一条 if (atk === 'anemo') → 扩散 ×1.25。三种 kind 各自带一个副作用：

反应倍率副作用实现
蒸发2.0 / 1.6无，纯伤害直接乘 DMG_BASE
超载1.5半径 104px 范围伤 14rxOverload() 遍历邻块

4.3 球的碰撞：最小重叠轴分离

const ox = (w / 2 + BALL_R) - Math.abs(b.x - (x + w / 2));
const oy = (h / 2 + BALL_R) - Math.abs(b.y - (y + h / 2));
if (ox <= 0 || oy <= 0) continue;
if (ox < oy) { b.x += (b.x < x + w/2 ? -ox : ox); b.vx = -b.vx; }
else          { b.y += (b.y < y + h/2 ? -oy : oy); b.vy = -b.vy; }
hitBlock(blk, run.el, DMG_BASE);
break;   // 一帧只处理一次碰撞，避免同一帧连撞两块导致穿透

先算两个轴的重叠深度，从重叠更浅的那个轴弹出 —— 这样从侧面撞和从上面撞的反射方向都是对的。break 不是优化，是正确性：不 break 时球会在一帧里连续弹两块，可能出现两块之间来回弹。

4.4 拍面：倾角决定反弹角

const hit = clamp((b.x - paddle.x) / PADDLE_HW, -1, 1);
const ang = clamp(paddle.aim + hit * 0.36, -Math.PI + 0.30, -0.30);
b.vx = Math.cos(ang) * BALL_SPD;
b.vy = Math.sin(ang) * BALL_SPD;

paddle.aim 本身由倾角决定（-π/2 + tilt），所以这是一个「双层控制」：左右移动决定接球点，上下键调倾角决定出球方向。命中点偏移再叠加 ±0.36 弧度，避免贴着边接球时方向完全由倾角决定，手感发死。

4.5 AI：预测落点 + 反解倾角

const land = predictLanding(b);          // 逐帧模拟侧墙/顶墙，求落点
const dx = land - paddle.x;
if (dx < -4) AIK.left = true; else if (dx > 4) AIK.right = true;
…
const ang = Math.atan2(blockCY(tgt) - b.y, blockCX(tgt) - b.x);
wantTilt = clamp(clamp(ang, -Math.PI + 0.4, -0.4) + Math.PI / 2, -TILT_MAX, TILT_MAX);

三段式：① 接球走位 ② 球接近拍面时按「目标块得分」反解倾角（得分 = 倍率×46 − 高度×0.055 − 水平距离×0.045 − 血量×0.55）③ 每 20 帧换一次元素（走 setEl(i, true) 静默通道，不弹提示条）。

5 · 星屑符咒 · 弹幕手记

五款里算法密度最高的一款。它的 AI 不是「躲最近的弹」，而是解一个两体最近接近点问题，再在 17 个候选方向里做字典序选择。

5.1 威胁表：相对速度的解析最近接近点

const rx = b.x - px, ry = b.y - py;
const rvx = pvx - b.vx, rvy = pvy - b.vy;
const rr = rvx*rvx + rvy*rvy;
let tt = rr > 1e-6 ? -(rx*rvx + ry*rvy) / rr : 0;
if (tt < 0) tt = 0; else if (tt > T.look) tt = T.look;   // look = 30 帧
const d = Math.hypot(rx + rvx*tt, ry + rvy*tt);

这是闭式解而非采样：把「玩家速度 + 弹速度」合成相对速度，直接求两条匀速直线的最近距离时刻 t* = −(r·v)/|v|²，钳到 30 帧视界内。

为什么不只看当前位置：只看当前位置的话，远处正朝你飞来的弹不算威胁，等它靠近已经来不及。
为什么不按「是否远离」排除：代码里留了实测记录 —— 只看弹速会把慢弹判成无害，同帧对照出现过 d=15（真实贴脸）与 d=74（调试快照）的分歧。

5.2 候选打分：字典序 + 自适应容差

for (const th of threats) {
  const relx = ux * step - th.vx, rely = uy * step - th.vy;
  let tt = vv > 1e-6 ? -(r0x*relx + r0y*rely) / vv : 0;
  tt = clamp(tt, 0, T.hor);                       // hor = 22
  const dd = Math.hypot(r0x + relx*tt, r0y + rely*tt) - th.r - player.hitR;
  if (dd < clear) clear = dd;                     // 安全余量（px）
  if (clear < -30) break;
}

17 个候选（16 个均分方向 + 原地不动）各算一个「安全余量」。关键在于不用加权和：

const tol = capClear > 45 ? 12 : capClear > 20 ? 6 : 2;
const thr = Math.max(0, capClear - tol);
…
const score = (c.ux*nx + c.uy*ny) * T.objDot      // 目标方向
            + (c.ux*AI.lx + c.uy*AI.ly) * T.inertia  // 惯性
            + (c.stay ? 1.5 : 0);

先取全局最优余量 maxClear，再按「余量越紧、容差越小」设阈值（12/6/2），只让接近最优的方向进入第二轮用目标点积排序。这样「为了瞄准站着不动」不会因为目标权重大而反噬安全性 —— 这是第一版 min(clear,70) + dot*24 踩过的死结。

5.4 弹型与节流

5.5 关卡链

三关，每关 3 波杂兵后出 BOSS；BOSS 状态机 enter → declare(90帧) → fight → next(40帧) → dying(120帧) → nextStage()。符卡时限单位换算是这类代码最容易错的地方：

c.timeSec  = c.time;        // 秒
c.timeLeft = c.time * FPS;  // 帧，FPS = 60
// 结算：bonus = round(200000 * (timeLeft / totalFrames)) + 80000

击破满分 28 万（时间奖励 20 万 + 基础 8 万），超时不加分。符卡表共 7 张（1 关 2 张、2 关 2 张、3 关 3 张），血量 130~280。

6 · 深渊回响

俯视角房间清怪 roguelite。结构上最不像前几款：它没有连续的战场，而是「一间房 = 一个 16×10 格的小迷宫」，清完走门进下一间。

6.1 楼层生成：线性房间数组，不是迷宫

const n = 5 + Math.min(4, Math.floor((run.depth || 1) / 2));
for (let i = 0; i < n; i++) {
  rooms.push({ i, cleared:false, visited:false,
    isBoss: (i === n - 1), w:16, h:10, x0:2, y0:2, spawned:false });
}

房间数 5~9（层数越深越多），所有房间尺寸完全相同。没有走廊、没有分支、没有 BFS —— 「进下一间」是把整张 map 重建，然后把玩家瞬移到新房中心。所以门只是触发器，不是可通行通道。

function descend() {
  run.depth++;
  clearFloor(); genFloor(); placeInRoom(0);
  run.transT = 100;   // 转场文字
}

run.depth 只在这一处自增，触发点是「打完本层最后一间房并踩到门」。

6.2 移动：双轴同时施加，再按轴回退

pl.x = clamp(pl.x, 24, W - 24);
pl.y = clamp(pl.y, 24, H - 24);
if (!isFloor(pl.x + Math.sign(pl.rx || ax || 0) * pl.r, pl.y)) pl.x -= ax * pl.spd * dt;
if (!isFloor(pl.x, pl.y + Math.sign(pl.ry || ay || 0) * pl.r)) pl.y -= ay * pl.spd * dt;

不是经典的「先移 X 再解 X、再移 Y 再解 Y」，而是同帧双轴先施加、再逐轴检查前缘采样点（当前坐标 + 朝向 × 半径）。前缘不在可走格就把该轴这一帧的位移撤回。isFloor 把 DOOR 也算可走，玩家才能踩进门格。

6.3 敌人 AI：四种运动学模板

类型行为
史莱姆直线追，撞墙置 bounce（不改速度，实际仍会穿墙环带）
蝙蝠追击角叠加 sin(t*0.18)*0.9 的正弦摆动
法师距离带控制：<110 后退、>170 前进、中间站定，每 84 帧三连点
石像慢速直追，撞墙沿 a+1.6 侧移
BOSSmove ⇄ attack 状态机，血量 ≤50% 进狂暴；阶段 1 十二向环射，阶段 2 七发扇形 + 狂暴十向环射

6.4 升级系统：轮盘法 + 一次三选一不重复

const pool = UPG.filter(u => (pl.levels[u.id] || 0) < u.max);
for (let k = 0; k < n; k++) {
  const idx = rndi(0, pool.length - 1);
  out.push(pool[idx]); pool.splice(idx, 1);   // 抽走即移除
}

16 项升级（7 武器 + 9 被动），满级自动从池里消失，全满时返回空数组并提示「没有可提升的东西」。宝箱品质用轮盘法（r -= p 累减）四档：木箱 1 选、铜箱 1 选、银箱 2 选、金箱 3 选；fortune 抬高时会重配分母，不是简单平移概率。

6.5 受击反馈：把渐变圆心推到受击来向的反面

const ox = -Math.cos(run.hurtDir) * W * 0.34;
const oy = -Math.sin(run.hurtDir) * H * 0.34;
const grad = ctx.createRadialGradient(W/2+ox, H/2+oy, 70, W/2+ox, H/2+oy, 470);
grad.addColorStop(0, 'rgba(255,91,110,0)');
grad.addColorStop(1, 'rgba(255,91,110,' + a.toFixed(3) + ')');

单次径向渐变同时编码了强度与方向：圆心被推到受击来向的反面，于是「伤害来的那一侧」离圆心最远、染色最深。外面再叠一层 a*0.14 全屏血雾和 a*0.8 的 4px 描边脉冲。

7 · 星轨防线 v2 · 缝合版

这一款的设计目标写在代码注释里：把「初版」的太空射击，与「星屑符咒」的符卡、「深渊回响」的升级箱缝合到一起。所以它的解析重点是三套系统怎么共存。

7.1 缝合三件套

来自机制缝合方式
星屑符咒STAGES + PAT 符卡表整张表搬过来，BOSS 的 run(b,dt) 直接调 PAT.ring/aimed
深渊回响UPG 升级池14 项，但 apply(w, p) 改成写派生参数对象 WS 而不是直接改玩家字段

7.2 参数派生：升级不直接改玩家，改一张「计算表」

function weaponStats() {
  return { dmg1:1.10, dmg2:0.85, cd:11, bspd:8.2,
           shots1:1, shots2:1, spread1:0.10, spread2:0.0,
           pierce:0, homing:0, fortune:0, powerMax:4.0, grazeMul:1 };
}
let WS = weaponStats();

// 升级：{ id:'w4', desc:'两武器伤害 +30%，射速 -12%',
//        apply(w){ w.dmg1 *= 1.3; w.dmg2 *= 1.3; w.cd *= 1.12; } }

好处是可重置：想重算一整套加成，只要 WS = weaponStats() 再按 levels 重放一遍 apply，不需要「记下原始值再反算」。代价是每次升级都要保证 apply 只写 WS，不能顺手改 pl（p3 迅捷是个例外，它写 p.spd）。

7.3 背击：一条几何判定决定 2.5 倍伤害

const shotAng = Math.atan2(s.vy, s.vx);
const fromBack = isFromBack(shotAng, e.shieldAng + e.shieldRot);
const mul = fromBack ? 2.5 : 1.0;
function isFromBack(shotAng, shieldAng) {
  let d = ((shotAng - shieldAng) % TAU + TAU) % TAU;
  return d > Math.PI * 0.5 && d < Math.PI * 1.5;   // 落在盾后的 180°
}

把角度差归一化到 [0, TAU) 再判断，避免负数取模的坑。这个函数被单独导出（__SL.isFromBack），因为判据要断言「绕后打伤害是正面的 2.5 倍」，不能让测试自己再实现一遍三角函数。

7.4 数值调优：注释里留着两次过冲

const AVOID = 3.4, AVOID_CAP = 16;
// 原来 5.2：134 发弹各贡献 5.2×w² 后 dx/dy 直接饱和 →
//   「躲弹」占了绝对主导，y 回不到瞄准线，第 2 关死两次。
// 试过 2.6：过头上头，变成「为了瞄准不躲」，第 1 关就被打死。
// 3.4 是两头之间量出来的折中。

这类注释在 v2 里很密集。它记录的其实是调参的方法论：先用实测找一个过头值、再找一个不足值，取中间；而不是凭手感微调。

7.5 保命优先级：分级而不是阈值

if (close >= 9 && pl.bombs > 0 && AI.bombCd <= 0) AI.wantBomb = true;
else if (close >= 6 && pl.rollT <= 0 && (dx || dy)) AI.wantRoll = true;
// close 1~5：不翻滚，走位躲就行，别浪费无敌帧

早版本是「贴脸 ≥3 发就翻滚」，结果 AI 冷却一好就立刻翻，等于一直在滚、从不停下瞄准。改成分级后：被围（≥9）先放炸弹（比翻滚划算，还有清屏收益），围上来（≥6）才翻滚，1~5 发靠走位。

8 · AI 接管的四条技术路线

五款游戏都有 AI 接管，但实现思路完全不同。这是整个仓库里最有技术含量的分歧点，也是「AI 能不能不作弊地打通关」这个问题的答案所在。

游戏方法候选/维度选择策略保命手段
初版 网格搜索（连续空间） 41 × 5 = 205 格 单标量 gain − danger×4.2 危险度 > 1.0 时冲刺硬扛
星屑符咒 射线候选 + 字典序 17 个方向 先安全阈值、再目标点积 贴脸 ≥5 放炸弹
符箓灵弹 解析预测 + 反解 1 个落点 + 1 个目标块 atan2 反解倾角 无（接球即保命）
深渊回响 势场（加权求和） 6 项力叠加 归一化后映射成摇杆行程 贴脸 ≥3 翻滚
星轨 v2 势场 + 分级保命 弹幕项 + 瞄准项 + 惯性 累积向量封顶 16 ≥9 炸弹 / ≥6 翻滚

8.1 共同的不作弊约束：AI 只写一个「虚拟摇杆」

function inp() {
  return { left: K.left || AIK.left, right: K.right || AIK.right,
           up: K.up || AIK.up, down: K.down || AIK.down };
}

五款都是这个形状：玩家输入对象与 AI 输入对象在同一个函数里合并，之后走同一套物理。Game.controlInput（初版）甚至只是一个 getter：

get controlInput() { return AutoPilot.on ? AutoPilot.input : Input; }

所以「AI 有没有作弊」是可以逐项验证的：判定半径、擦弹半径、无敌帧、移速、单帧位移上限 —— 开关 AI 前后这些量必须逐个相同。判据就是这么写的，实测单帧位移 ≤ 7.8px（等于玩家移速）。

8.2 为什么「敌弹」和「敌机」不能用同一套威胁模型

初版的注释里有一段价值很高的实测记录：如果敌机也按 time-to-hit 推演，AI 会把「站到它下面开火」判成高危 —— 那格危险度 8.01 × 4.2 = −33 分，而击杀收益只有 1.34。结果 AI 宁可站着不动让敌机漏掉，87% 的命丢在漏怪上。

于是改成两套数学：

对象模型理由
敌弹（不可打掉）time-to-hit，1.5 秒视界，紧迫度 1/(t+0.08)必须真躲
敌机（可以打掉）只在 0.5 秒内落到头上才算威胁，三次衰减打掉比躲开更优
这条经验可以直接迁移：在「威胁可以消除」的场景里，用躲避模型会得到保守到自毁的策略。弹幕游戏里子弹不可消、敌人可消，所以必须分开建模。

8.3 输出幅度也是一个参数

const mag = bestClear > 0 ? 1 : 0.72;   // 有余量就全速，被围死才微调
return { ax: bx * mag, ay: by * mag };

星屑符咒这里踩过坑：早版本按「余量越紧走得越慢」设计，结果被围时慢慢挪，反而死了。现在改成「只要还有一点余量就全速冲出去」。

9 · 二倍速的三种写法

五款都有二倍速，但实现分三档。这一节值得单独看，因为「怎么实现二倍速」直接决定了判定准不准。

写法哪几款做法风险
A · 全局缩放 dt 初版 step = min(dt * timeScale, MAX_DT) 缩放后必须再钳一次，否则单步位移翻倍会穿透
B · 固定步长累加器 星屑 / 深渊 / 星轨 acc += frames * SPEED; while(acc>=1){ update(1); acc--; } 需要 MAX_STEP 防追帧雪崩
C · 累加器 + 独立 tick 符箓灵弹 抽成 tick(dtFrames)，判据可直接驱动 guard 上限写成 8 会把 tick(10) 截断

9.1 为什么不能直接 update(dt*2)

星屑符咒的注释算过这笔账：自机弹 3.6px/帧、判定圆直径 7px，dt=2 时单步 7.2px，已经跨过整个判定圈；深渊回响同理 —— 最快敌弹 3.1px/帧，玩家有效受击半径 10×0.62 + 5 ≈ 11.2px，dt=2 时 6.2px 在部分入射角会一步跨过。固定步长让物理步长恒为 1，判定精度与倍速彻底解耦。

9.2 累加器的三个隐藏细节

function advance(frames) {
  if (run.scene !== 'play' || run.paused || run.over || run.choosing) { acc = 0; return 0; }
  acc += frames * SPEED;
  let n = 0;
  while (acc >= 1 && n < MAX_STEP) {
    if (run.scene !== 'play' || run.paused || run.over || run.choosing) break;
    update(1); acc -= 1; n++;
  }
  if (acc > MAX_STEP) acc = 0;
  return n;
}
  1. 入口闸门要 acc = 0。不清零的话暂停期间 acc 一直涨，解除暂停瞬间补跑好几帧。
  2. 循环体内要再判一次。因为 update 内部可能触发 gameOver() 或 showUpgrade()，必须当帧就停。
  3. 切换倍速、重开局都要清零 acc。否则带着旧的小数相位跳变。

10 · 解读中发现的 3 处缺陷

解析代码时对着「定义 → 调用」做了交叉核对，发现深渊回响有 3 处逻辑在跑、但玩家感知不到的缺口。它们都不影响 44 项判据（说明判据覆盖不到这几处），但影响实际游玩。

① 敌人子弹完全不渲染。
drawEBullets() 定义在 1481 行，做了双层 lighter 光晕，但 draw()（1183–1200）的调用表里没有它：
drawFloor → drawDoors → drawDrops → drawChests → drawBullets → drawEnemies → drawPlayer → drawParts → drawHurtOverlay → drawHUD
后果：法师、BOSS 发的弹真实存在、真实扣血，但屏幕上什么都没有。玩家只能看到自己莫名其妙掉血。
修复：一行 —— 在 drawEnemies() 之后补 drawEBullets();。但要注意这会让游戏明显变难（凭空出现的伤害变成可见威胁），需要同步复核难度，不是纯 bugfix。
② 翻滚时不会撞墙。
pl.rx/ry 在 616 行赋值后从不清零，而碰撞回退量写的是 ax * pl.spd * dt（手操位移），不是 pl.rx * dt（翻滚位移）。松手翻滚时 ax = 0 → 回退量 0 → 只剩 clamp(24, W-24) 的屏幕边界。
另外前缘探针用的是 pl.rx || ax，而 rx 永不清零，所以翻滚结束后探针方向永远停在最后一次翻滚的方向，与当前移动方向无关。
修复：翻滚结束（rollT 归零）时把 rx/ry 清零，并把回退量改成「本帧实际位移量」。
③ 法师的「三连点」只打出 1 发。
1002 行生成三发时给了 delay: i * 9，但全文没有任何地方递减 b.delay（只在 771/1485/1492 被读）。于是第 2、3 发永久 delay > 0：既不渲染、也不参与判定，白白飞出场外。
修复：在 updateEBullets 里补 if (b.delay > 0) { b.delay -= dt; continue; }。这一条修完法师会真的变成三连发，难度同样要复核。
这三条的共同点值得记一笔：「定义了却没人调用」和「字段只写不读」是静态检查抓不到的一类 bug。语法通过、判据全绿、页面能玩，但机制衰减或消失。可行的自动检查是对每个 function drawXxx 断言它在 draw() 里被引用一次，对每个「有 delay: 赋值」的字段断言存在递减语句。

11 · 判据如何验证这些实现

183 项判据不是「跑一遍不报错」，而是每一条都指向一个具体机制。五个 verify/smoke.js 共用同一套基础设施。

11.1 测试基础设施

node verify/smoke.js index.html __TP

起本地 HTTP 服务 → 启动 headless Edge → 用原生 WebSocket 直连 CDP → 轮询 typeof window.__TP !== 'undefined'。不依赖 puppeteer。所有游戏都导出了 freeze() / step(n)，让测试成为唯一时钟。

11.2 判据的三个层次

层长什么样例子
硬断言（机制触发）某个动作必须产生某个状态变化「敲光墙 → wave 加 1」「清完最后房间 → depth 加 1 且游戏未结束」
数值对照（同初始条件比伤害）控制变量，只改一个因素「蒸发真伤害：同元素 90 / 水打火 80 / 火打水 84」
统计量（多轮取中位数）跑 N 轮，看分布「AI 连续 3 轮各 90 秒，每轮破阵 ≥ 2」；「AI 9/9 通关，存活中位 178 秒」

11.3 反作弊判据怎么写的

// 开关 AI 前后，这些量必须逐个相同
